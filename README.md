# CarBridge

Автомобильный маркетплейс: два связанных рынка — автомобили в наличии в
Бишкеке и автомобили из Китая под заказ, с прозрачным калькулятором полной
стоимости доставки и подбором по бюджету. См. полное ТЗ в истории задач;
ключевые решения по объёму MVP — ниже.

`CarBridge` — рабочее имя-заглушка. Меняется одной переменной окружения
(`NEXT_PUBLIC_SITE_NAME`) без правок кода.

## Стек

- **Next.js 14 (App Router) + TypeScript** — фронтенд, SSR/SSG, Server Actions
- **Supabase** — Postgres + Auth + Storage + Row Level Security
- **Tailwind CSS**, тема сгенерирована из `design-tokens.json`
- Хостинг: Vercel (фронтенд) — по спецификации, база данных переезжает на
  self-hosted Supabase (borneo.kg) без изменения кода (см. `.env.example`)

Ничего проприетарное для облачного Supabase не используется (обычный
Postgres + `@supabase/supabase-js`/`@supabase/ssr`), поэтому self-host на
Фазе 2/3 — это `pg_dump`/`pg_restore` + переменные окружения, без правок кода.

## Быстрый старт

```bash
npm install
cp .env.example .env.local   # заполнить ключи Supabase-проекта
```

В Supabase-проекте выполнить миграции (SQL Editor или Supabase CLI):

```bash
# порядок важен
supabase/migrations/0001_init.sql
supabase/migrations/0002_storage.sql
supabase/migrations/0003_verification.sql
supabase/migrations/0004_reviews_rating.sql
supabase/migrations/0005_tariff_privileges.sql
supabase/migrations/0006_banners.sql
supabase/seed.sql              # справочники, тестовые ставки калькулятора, статичные страницы
```

Если проект уже развёрнут — накатывайте только новые файлы миграций, которых
у вас ещё нет (по номеру), `seed.sql` тоже безопасно перезапускать (там upsert).

```bash
npm run dev       # http://localhost:3000
npm run typecheck
npm run lint
npm run build
```

Чтобы попасть в `/admin`, зарегистрируйте пользователя через `/register`, а
затем вручную обновите его роль в Supabase:

```sql
update public.users set role = 'admin' where id = '<user-id-из-auth.users>';
```

## Что реализовано (Этап 1 — MVP, + часть Этапа 2)

Объём согласован с заказчиком: полный MVP по разделу 11 ТЗ, плюс из Этапа 2 —
страницы дилеров/компаний (остальное — платные тарифы с оплатой — по
прежнему за рамками этого прохода, данные под них уже заложены в схему).

- **Каталог** (`/cars`) — оба рынка, фильтры (рынок/марка/кузов/год/пробег/
  цена/топливо/коробка/статус), bottom-sheet фильтры на мобильном,
  постраничная навигация. Подразделы карты сайта (Новые/С пробегом/
  Электро/Гибриды/В наличии/Под заказ) — это преднастроенные фильтры того
  же каталога через query-параметры, а не отдельные страницы.
- **Карточка объявления** (`/listings/[id]`) — SSR, разбивка цены для
  авто из Китая, фото/видео, лид-форма, WhatsApp-кнопка, счётчик просмотров.
- **Раздел «Китай»** (`/china/*`) — хаб, калькулятор стоимости, статичные
  страницы «Как купить», «Доставка», «Таможня», «Проверенный автомобиль»
  (markdown из таблицы `static_pages`, редактируется в `/admin/pages`).
- **Калькулятор** — ставки логистики/брокера/таможни читаются из таблицы
  `calculator_rates` (редактируется в `/admin/rates`), не хардкодятся в UI.
  См. «Отклонение от ТЗ» ниже про поле цены в Китае.
- **Подбор по бюджету** (`/budget`) — подбор из каталога + лид-форма, если
  впритык ничего не нашлось.
- **Главная** — два равнозначных CTA, мини-калькулятор (марка+модель →
  переход в полный калькулятор), виджет подбора по бюджету, витрина обоих
  рынков.
- **Личный кабинет продавца** (`/dashboard/*`) — CRUD объявлений, до 20 фото
  через Supabase Storage, переключение статуса, счётчик просмотров, лиды по
  своим объявлениям, запрос тарифа (ручное подтверждение админом),
  настройки профиля.
- **Привилегии тарифов реально работают** (спецификация §5.7), не только
  запрашиваются/подтверждаются: лимит активных объявлений — 5 на бесплатном,
  30 на PRO, без ограничения на «Дилер» (проверяется по активной подписке
  самого пользователя и подписке его компании — `getListingLimit()` в
  `src/lib/data/subscriptions.ts`, дублируется в `createListing` и на
  странице `/dashboard/listings`, чтобы счётчик не расходился с реальным
  ограничением). Тариф «TOP» — разовое продвижение конкретного объявления
  (не аккаунта целиком): кнопка «Продвинуть в TOP» у объявления в
  `/dashboard/listings` создаёт заявку с `listing_id`, админ подтверждает её
  в `/admin/subscriptions` (там же видно, какое именно объявление), после
  чего у объявления выставляется `is_top` — оно поднимается в начало
  каталога и ленты («В наличии»/«Из Китая» на главной) и получает
  бейдж/рамку TOP на карточке. `listing_id` в `subscriptions` — тоже claim
  владения, проверяется и на уровне server action (`requestPlanUpgrade`), и
  на уровне RLS (`owns_listing_or_null`, по аналогии с `owns_dealer_or_null`
  для `dealer_id`); флаг `is_top` защищён от прямого изменения владельцем
  тем же триггером, что и поля верификации. Известное упрощение MVP: нет
  cron-джобы для сброса `is_top`/автопереноса подписки в `expired` по
  истечении `expires_at` — админ снимает вручную, как и остальные тарифы.
  Привилегия «Статистика» (PRO) / «Аналитика» (Дилер) — страница
  `/dashboard/stats`: активные объявления, суммарные просмотры, заявки по
  статусам, заявки за 30 дней, топ-10 объявлений по просмотрам. Доступ
  проверяется той же `getActivePlans()` (`hasStatsAccess()`), что и лимит
  объявлений; на бесплатном тарифе страница показывает предложение
  перейти на PRO/Дилер вместо данных. Данные читаются через RLS, уже
  ограничивающий `listings`/`leads` до записей текущего пользователя —
  дополнительная фильтрация по `user_id`/`dealer_id` в запросах не нужна.
- **Баннерная реклама** — 5-й источник монетизации из ТЗ, до этого прохода
  никак не смоделированный. Отдельная таблица `banners` (не завязана на
  `subscriptions` — у баннера нет привычного плана/лимита, только один
  рекламный слот на площадку за раз): продавец подаёт заявку в
  `/dashboard/ads` (название, ссылка, картинка, место размещения — главная/
  каталог/раздел «Китай»), картинка загружается сразу в Storage (бакет
  `banner-media`, папка по `user_id` — заявки на баннер ещё не существует
  на момент загрузки файла, в отличие от фото объявлений/логотипа дилера,
  поэтому папка ключуется по загрузившему, а не по будущей строке).
  Админ подтверждает/отклоняет в `/admin/banners` (`updateBannerStatus()`,
  та же ручная схема оплаты, что и у тарифов), после чего баннер
  показывается через `<AdBanner placement="…">`, вставленный в общие
  `HomeContent`/`CarsPageContent`/`ChinaHubContent` — значит, автоматически
  и на `/en`-зеркале тоже, без дублирования кода. На каждом месте
  размещения показывается только один баннер (последний подтверждённый),
  без ротации/карусели — сознательное упрощение MVP.
- **Админка** (`/admin/*`) — модерация (approve/reject), ставки калькулятора,
  все лиды, заявки на тарифы, редактор статичных страниц, справочник марок
  и моделей (`/admin/brands`, с автоподсказками в форме объявления и
  фильтрах каталога через `<datalist>`).
- **«Проверенный автомобиль»** (спецификация §5.6) — из модерации админ
  ставит/снимает бейдж, указывает кто проверял, заключение по состоянию и
  отмечает, какие из уже загруженных фото/видео объявления — диагностика
  (`VerificationEditor`). На странице объявления это разворачиваемый блок:
  VIN, пробег, дата и инспектор, заключение, фото/видео диагностики.
  `is_verification` на фото/видео и сами поля проверки на `listings`
  защищены триггером — их может менять только админ, даже при прямом
  запросе владельца объявления к API.
- **Компании** (`/companies`, `/companies/[slug]`) — каталог дилеров
  (бейдж «Проверенный поставщик», рейтинг, число объявлений) и страница
  компании со всеми её активными объявлениями. Продавец заводит профиль
  компании в `/dashboard/company` (описание, контакты, логотип через
  Supabase Storage) и опционально публикует объявление от её имени —
  `dealer_id` на объявлении проверяется и на уровне server action, и на
  уровне RLS (`owns_dealer_or_null`), чтобы нельзя было приписать себе
  чужую компанию через прямой запрос с anon-ключом. На странице компании —
  отзывы: список + форма (только для вошедших, RLS требует `auth.uid()`),
  звёздный рейтинг компании (`dealers.rating`) пересчитывается автоматически
  триггером по факту отзывов, а не выставляется вручную. Модерация спама —
  `/admin/reviews`.
- **Избранное** — вне модели данных ТЗ (в разделе 6 нет таблицы `favorites`),
  сделано через `localStorage` на устройстве, чтобы не пустовал пункт нижней
  навигации; полноценная серверная реализация — на Этап 2.
- **Авторизация** — Supabase Auth (email/password), роль хранится в
  `public.users`, RLS запрещает самостоятельно повысить роль.
- **RLS** включена на всех таблицах (см. `supabase/migrations/0001_init.sql`).
- **i18n** — `ru` (без префикса, как раньше — `/cars`) и **`/en`** зеркалит
  весь путь покупателя: главная, каталог+фильтры, объявление, раздел
  «Китай» (хаб, калькулятор, 4 статичные страницы), подбор по бюджету,
  компании, о площадке. Тексты — из `src/lib/i18n/dictionaries/{ru,en}.json`;
  общие компоненты (`FilterPanel`, `ListingCard`, `LeadForm`,
  `CalculatorForm`, `PriceBreakdown`, `StatusBadge`, `StaticPageContent`)
  принимают `locale` и работают на обоих деревьях без дублирования логики —
  у каждой ru/en пары страниц есть общий `*Content.tsx`, а `page.tsx` — тонкая
  обёртка с `locale="ru"`/`"en"`. Переключатель RU/EN — в шапке
  (`LocaleSwitcher`, определяет текущий раздел по `usePathname()`).
  **Кабинет продавца, админка, вход/регистрация остаются только на русском**
  — ими пользуются продавцы и модераторы в Кыргызстане, а не покупатель,
  для которого сделан `/en`; это осознанная граница объёма, не недосмотр.
  Английские тексты статичных страниц (`static_pages`, locale='en') — в
  `supabase/seed.sql`; если для какого-то slug английской строки ещё нет,
  `StaticPageContent` показывает русскую как запасной вариант, а не 404.
  Добавление третьего языка (`/kz`, `/uz`) — новый файл словаря + новая
  папка-зеркало маршрутов, без переписывания компонентов.
- **Аналитика воронки** — `trackEvent()` пишет события (`calculator_open`,
  `calculator_submit`, `lead_submit`, `budget_search`) в таблицу
  `analytics_events`.
- **Rate limiting** — простой лимитер на отправку лидов (`src/lib/rate-limit.ts`),
  подходит для одного инстанса; на масштаб — заменить на общий стор.

## Дизайн-система

Все визуальные константы — в `design-tokens.json`, Tailwind (`tailwind.config.ts`)
читает их напрямую. Будущее мобильное приложение (React Native/Flutter) может
читать тот же JSON. Вёрстка mobile-first (375–420px), нижняя навигация из 5
пунктов, минимальная зона нажатия 44×44px (`min-h-touch`/`min-w-touch`),
фильтры — полноэкранный bottom sheet на мобильном.

## Модель данных

`supabase/migrations/0001_init.sql` — полная схема по разделу 6 ТЗ:
`users`, `dealers`, `brands`/`models`, `listings`, `listing_photos`,
`listing_videos`, `calculator_rates`, `leads`, `subscriptions`, `countries`,
`static_pages`, `app_settings`, `reviews` (схема есть, UI не строился —
опционально для MVP по самому ТЗ), `analytics_events`. RLS-политики на
каждой таблице; `0002_storage.sql` — бакеты Storage для фото объявлений и
логотипов дилеров; `0003_verification.sql` — поля под детали проверки
(`verified_by_name`, `is_verification` на фото/видео) и защита этих полей
триггером (только админ); `0004_reviews_rating.sql` — отзывы дилеров и
автопересчёт рейтинга; `0005_tariff_privileges.sql` — `listings.is_top`,
`subscriptions.listing_id` (какое объявление продвигает заявка на TOP),
RLS-функция `owns_listing_or_null` и расширение триггера защиты полей на
`is_top`; `0006_banners.sql` — таблица `banners` (баннерная реклама, 5-й
источник монетизации из ТЗ) и Storage-бакет `banner-media`.
**Применять миграции по порядку номеров** — каждая следующая
рассчитана на то, что предыдущие уже накатаны на боевой проект.

## Отклонения от ТЗ и осознанные допущения

- **Калькулятор запрашивает цену авто в Китае как отдельное поле.** В разделе
  6 нет таблицы с эталонными ценами по маркам/моделям/комплектациям — только
  `calculator_rates` (логистика/брокер/таможня). Без такого справочника
  система не может сама «знать» цену конкретного авто, поэтому калькулятор
  принимает её на вход (пользователь или менеджер), а из БД тянутся именно
  логистика/оформление/таможня — как и требует ТЗ.
- **`customs_formula`** хранится как текстовый комментарий (как выведена
  пошлина для admin-аудита), а сама пошлина — числовое поле `customs_duty`
  за бракет. Вычисление формулы на лету в рантайме не делается — это
  риск (eval непроверенных выражений) без ощутимой пользы против плоской
  ставки за диапазон.
- **Платные тарифы с реальной оплатой** — сознательно вне этого прохода
  (интеграция платёжного шлюза — отдельный этап после проверки спроса,
  прямо как написано в ТЗ §5.7). Ручной запрос тарифа и ручное
  подтверждение админом уже работают (`/dashboard/billing`,
  `/admin/subscriptions`), и сами привилегии тарифов (лимиты объявлений,
  продвижение TOP) реально применяются после подтверждения — см. выше.
## Известные ограничения перед продакшеном

- `npm audit` отмечает уязвимости в цепочке Next.js для всей линейки до
  16.3.x включительно (мажорный апгрейд с breaking changes в App Router —
  async `cookies()`/`params`/`searchParams`). Для тестовой Фазы 1 оставлено
  на `14.2.35` (последний патч ветки 14); обновление до патченной версии —
  сделать перед реальным продакшен-релизом.
- Rate limiting лидов — in-memory, не переживает несколько serverless-инстансов
  Vercel; для продакшена — вынести в общий стор (например, Upstash Redis).
- Реальные ставки логистики/таможни в `supabase/seed.sql` — иллюстративные
  плейсхолдеры (см. раздел 12 ТЗ — этого от заказчика ещё не получено).
- **Производительность — два прохода.** Первый: `supabase.auth.getUser()`
  (сетевой запрос к Supabase Auth, в отличие от `getSession()`, читающей
  только cookie) дублировался на каждый рендер — в `Header`, в layout
  кабинета/админки и часто ещё раз в самой странице; продублированные
  запросы схлопнуты через `cache()` из `react`
  (`getAuthUser()`/`getCurrentUser()` в `src/lib/data/profile.ts`, кеш
  только на время одного запроса — не влияет на актуальность/безопасность),
  N+1 (подсчёт объявлений на дилера в `getDealers()`) и последовательные
  запросы, которые не зависят друг от друга (`getListingLimit`,
  `getSellerStats`, страница «Мои объявления»), свёрнуты в `Promise.all`.
  Этого оказалось недостаточно — и второй, более глубокий проход вскрыл
  причину: `createServerSupabaseClient()` вызывает `cookies()`, а это
  заставляет Next.js рендерить **весь** роут динамически на каждый запрос,
  без всякого кеширования — даже страницы, которым авторизация вообще не
  нужна (`Header` дергал её на каждой странице сайта). Из-за этого
  `export const revalidate = 60`, уже стоявший на странице объявления,
  ничего не давал — сборка (`npm run build`) до этого момента помечала
  вообще все роуты как `ƒ (Dynamic)`, ни одного `○ (Static)`. Исправлено:
  - `Header` больше не делает серверную проверку авторизации — кнопка
    «Войти»/«Кабинет» вынесена в клиентский `HeaderAuthButton`
    (`src/components/layout/Header.tsx`), читает сессию из браузерного
    клиента без похода на сервер. Это единственное, что раньше делало
    *весь* сайт (через корневой layout) недоступным для кеширования.
  - Данные, которые видно всем и без авторизации (одобренные объявления,
    дилеры, бренды/модели, статичные страницы, активные баннеры, отзывы),
    теперь читаются через `createPublicSupabaseClient()`
    (`src/lib/supabase/public.ts`) — обычный anon-клиент без `cookies()` —
    вместо `createServerSupabaseClient()`.
  - Главная, каталог компаний, хаб «Китай», статичные страницы (`/about`,
    `/china/how-to-buy` и т.д.) получили `export const revalidate = 60` и
    теперь реально кешируются (после этого прохода `npm run build`
    показывает их как `○ (Static)`), а не бьют в Supabase на каждый заход.
  - Осознанно не тронуто: `/cars` (фильтры каталога живут в
    `searchParams`, Next.js всегда рендерит такие страницы динамически);
    `/listings/[id]` (RLS отдаёт владельцу его собственное объявление на
    модерации, даже неодобренное — «Открыть объявление» из кабинета до сих
    пор должно работать, поэтому эта страница осталась на
    `createServerSupabaseClient()` и не кешируется); кабинет/админка
    (заведомо персонализированы, кешировать нечего).
  - `src/middleware.ts` (обновление сессии Supabase из cookie) раньше
    выполнялся на *каждом* запросе, включая теперь-статичные страницы,
    которым это вообще не нужно (Header больше не читает cookie серверно —
    см. выше). Сузил `matcher` до `/dashboard`, `/admin`, `/login`,
    `/register`, `/auth/*` — на остальных страницах сессию поддерживает
    свежей автообновление токена в браузерном Supabase-клиенте (оно и так
    всегда активно — `HeaderAuthButton` монтируется на каждой странице).
  Первый заход на статичную страницу после деплоя или после истечения
  60-секундного окна кеша неизбежно будет чуть медленнее — Vercel в этот
  момент реально генерирует и кеширует страницу заново; все заходы внутри
  этого окна должны отдаваться из кеша почти мгновенно. Если же медленно
  *каждый* заход без исключения — почти наверняка дело уже не в коде, а
  в самом проекте Supabase: проверьте его регион (должен быть близко к
  региону функций Vercel, по умолчанию US East) и не заснул ли бесплатный
  проект от простоя (первый запрос после паузы занимает до 10+ секунд,
  пока он поднимается) — на это код повлиять не может.
